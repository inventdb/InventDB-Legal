1. THE PORT GUARD — backend refuses to share a port
================================================================================
PMS keeps port 8000 and Vite 5173. Do NOT renumber them — Legal moved to 8010/5174
precisely so PMS could keep these. What PMS is missing is the guard.

The bug: both Flask's dev server and waitress set SO_REUSEADDR, and on Windows
that lets a second process bind an address another process is already listening
on — no EADDRINUSE, no warning. Connections then land on whichever socket the
stack picks, so a second app on the same port does not fail to start, it
*intermittently answers for the first one*. When this happened, the Legal frontend
proxied /api straight into PMS's entity registry and every module came back
`404 Unknown entity: properties` while both servers reported themselves healthy.

Add to backend/app/main.py (module level, `import socket` at the top):

    def _refuse_occupied_port(host: str, port: int) -> None:
        # Skip in Werkzeug's reloader child: the parent binds the socket and
        # hands the descriptor down, so the child would find "its own" port
        # occupied and refuse to start.
        if os.environ.get("WERKZEUG_RUN_MAIN") or os.environ.get("WERKZEUG_SERVER_FD"):
            return
        probe_host = "127.0.0.1" if host in ("", "0.0.0.0", "::") else host
        with socket.socket() as sock:
            sock.settimeout(0.5)
            if sock.connect_ex((probe_host, port)) != 0:
                return
        raise SystemExit(
            f"Port {port} is already serving something on {probe_host}.\n"
            f"Starting here anyway would not fail -- on Windows both processes can\n"
            f"hold the port, and requests would be split between them at random.\n"
            f"Stop the other server, or pick another port:  API_PORT=8001"
        )

Call it from `run()` in main.py and from the `__main__` block in backend/wsgi.py,
before binding. NOTE: the WERKZEUG_RUN_MAIN / WERKZEUG_SERVER_FD exemption is not
optional — without it the guard fires on every `debug=True` start.

Tests (backend/tests/test_app.py), five of them:
  - a free port starts normally
  - a port something else is serving raises SystemExit naming the port and API_PORT
  - `0.0.0.0` is probed on 127.0.0.1, not connected to directly
  - the reloader child is exempt (both env vars)
  - Settings().api_port is still 8000

2. SPLIT THE MODULE-WALK TEST — frontend/e2e/views.spec.ts
================================================================================
`views.spec.ts` has one test ("every module offers one, defaulting to the full
list") that loops over all ten modules, spending ten navigations against a single
45s timeout. Under `fullyParallel` that budget is shared with whatever the other
workers are doing, so it fails on machine load rather than on a defect — it failed
for us, then passed at `--workers=1`, which is the signature.

Turn the loop inside out: keep the same assertion, but generate one test per
module so each carries its own budget and they run in parallel.

    for (const { name, plural } of MODULES) {
      test(`${name} offers one, defaulting to the full list`, async ({ page }) => {
        await page.goto(`/${name}`);
        await expect(page.locator(trigger)).toHaveText(
          new RegExp(`All ${plural}`, "i")
        );
      });
    }

Keep the assertion byte-for-byte as it is today — only the loop moves. PMS's ten
plurals carry no regex punctuation, so the bare `${plural}` is safe here. (Legal
needed an `escapeRegExp` around it because "Trust Ledger (CTA)" and "Costs &
Disbursements" do; if you ever add a plural with parentheses, add the escape.)

3. IMPORT — the run must outlive the room
================================================================================
PMS already has the result bar (the green "Created N records in X" panel with
View/Import-another and the plan signature). Keep it. Everything below is missing.

THE BUG. The import run is owned by the Import page's own component state, and
`useCancelableRun` aborts on unmount unless told otherwise. So navigating to
another module mid-import kills the run AND throws away every trace of it. The
batches already sent are real committed records — on a large import you leave
thousands of rows in the database with nothing anywhere saying so, and an empty
dropzone inviting you to import the same file again.

3a. Move the run OUT of React — new file frontend/src/pages/importRun.ts

A module-level singleton the page subscribes to via `useSyncExternalStore`.
Navigation cannot touch it. It owns:
  - state: { running, done, total, message, types, sig, error }
  - subscribeImport(fn), getImportState()  — getImportState must be
    identity-stable between emits or React throws "getSnapshot should be cached"
  - startImport(plan, onFinished), cancelImport(), resetImport()
    resetImport refuses while a run is in flight.
Only one import at a time — two would race on the same types with no way to tell
whose rows landed.

The page then reads `done`/`types`/`sig` from the store instead of local state,
and `create()` / `importAll()` build a plan and hand it to `startImport`.

3b. Retry the batch, not the import

The shared axios client has a 60s timeout. A 500-row bulk insert can legitimately
take longer, and that one rejection used to abandon every batch behind it — which
is what "only a few uploaded" looks like. Per batch: up to 3 attempts with
backoff, on an explicit `timeout: 10 * 60_000`. An AbortError is not retried. If a
batch ultimately fails, stop and say where:
    "<detail> — stopped after 41,500 of 68,715 rows."
NOTE: "Import failed" over a half-written table leaves the operator with no idea
what is in the database. The count is the useful half of that message.

3c. Guard the unload

Client-side navigation is survivable; a document unload is not — the JS context
goes and every in-flight batch dies with it. While a run is in flight, add a
`beforeunload` listener; remove it when the run settles.

3d. Announce completion from anywhere

`ToastProvider` sits above the router, so `onFinished` firing a toast reaches the
user wherever they have navigated to. Verify that ordering in main.tsx before
relying on it.

3e. Show the run when you come back

The Import page returns early when there is no workbook (`if (!wb)`), so a user
returning mid-import hits the empty dropzone. In that branch, before the dropzone:
  - if `run.running`  -> the progress panel (3f)
  - else if `run.message` -> the result bar, with a Dismiss that calls resetImport
  - hide the dropzone entirely while a run is in flight: only one import goes at a
    time, so a dropzone that can take a file but never offer an Import button is a
    dead end.

3f. A real progress panel — do NOT restyle the shared ActionProgress

`ActionProgress` is used by Analyze, Reports and Files; changing it moves four
rooms at once. Build a local `ImportProgress` for the Import room:
  - "Importing rows" in bold, then "12,638 of 68,715 · 18%"
    NOTE: grouped digits and a percentage. The shared strip renders a raw
    `12638/68715`, which is unreadable at a glance.
    NOTE: `font-variant-numeric: tabular-nums` on the count, or it jitters
    sideways on every batch.
  - a full-width 6px bar with role="progressbar" and aria-valuenow
  - Cancel as an ordinary ghost button on the right — the shared one renders it as
    red text, which reads as an error rather than a choice
  - a quiet caption: "Keeps running while you work elsewhere — batches already
    sent are saved."

3g. Regression test — frontend/e2e/import-navigation.spec.ts

Two tests, and they are the point of this section:
  - start a ~1,200-row import against a slowed mock, click a module link mid-run,
    assert the batch count KEEPS RISING while away, return, assert the progress
    panel is on screen (not the dropzone), and that all batches land: [500,500,200]
  - a run that finishes while the user is on another module still toasts there
NOTE: switch modules by CLICKING THE SIDEBAR, not `page.goto`. A goto is a
document reload — it tears down the JS context and tests a different failure.

4. REPORTS — a count by the list, and multi-select delete
================================================================================
4a. Count beside the list

The page head has a "N reports" pill, but it goes stale the moment you search: it
keeps saying 6 while the list shows 1. Add a toolbar row directly above the
library list (between the search box and the list) carrying the count, and make it
honest under a filter: "2 of 6 reports" when filtered, "6 reports" otherwise.

4b. Selection

A checkbox per row, plus a select-all in that toolbar with a proper indeterminate
state. Hold the selection as a Set of library keys, not of items, so it survives
the list refetching. Prune keys the library no longer holds when `items` changes.

NOTE — the important one: **select-all covers only the VISIBLE rows.** A select-all
that quietly swept in rows a search had filtered out would be a bulk delete of
records the operator cannot see. Selection persists across clearing the search;
it just never grows to include what was hidden.

NOTE: ticking a row must not navigate to it, and opening a row must not clear the
selection. Both are easy to get wrong.

4c. Bulk delete

When anything is selected the toolbar shows "N selected" and a danger button
"Delete N". The confirm dialog NAMES them — "Delete 2 reports? — "Owner
Statement", "Rent Roll". Live reports are removed from your InventDB instance, for
everyone." `Delete 6 reports?` is not a question anyone can answer safely.

New mutation `useDeleteReports` in frontend/src/reports/api.ts:
  - takes a list of { kind: "template" | "snapshot", … , name }
  - deletes SEQUENTIALLY and invalidates ONCE at the end (onSettled, so a run that
    failed part-way still re-reads). NOTE: `useDeleteReport` in a loop invalidates
    on every success — clearing a library of 200 would fire 200 list refetches
    while the deletes were still running.
  - catches per item and returns { deleted, failed: string[] }, so a partial
    failure is reported BY NAME: "Deleted 4. Could not delete 2: Rent Roll, …".
    The operator needs to know which survived, not just a total.

5. FILES — bring the upload up to SOAR's
================================================================================
The Files room's upload is several steps behind SOAR's Files drive. Six gaps.

THE REAL DEFECT FIRST: the room demands a **Record id** before it will upload
anything — but files with no parent record live at `<type>/_vault`, InventDB's own
convention and what SOAR uploads into. The room cannot create the kind of file it
is already displaying. Make the record optional and default to `_vault`.

5a. A persistent dropzone above the list, always visible, with SOAR's wording:
    "**Drop files or a folder** here, or click to choose — you'll confirm where
     they live before anything uploads. Folders keep their structure."
    NOTE: today the only drop target is the file list, which gives no sign the
    room accepts anything at all.

5b. Two buttons: "Upload files" (primary) and "Upload folder". Two hidden inputs —
    `webkitdirectory` cannot share an input with a plain file picker. Set it via a
    ref callback (`el.setAttribute("webkitdirectory", "")`), and type the ref as
    `HTMLInputElement | null` or TS rejects the assignment.

5c. A staging panel — picked, NOT yet sent. Amber, not the brand colour: every
    other panel reports what is stored; this is the one showing bytes still only in
    the browser.
      - head: "Ready to upload — N files" + a "NOT UPLOADED YET" tag
      - a scrollable list (max ~180px) of monospace `webkitRelativePath || name`
        with size and a ✕ to remove, "…and N more" past 200
      - destination: Namespace (read-only — the app pins it server-side, so a
        picker it cannot honour would be a control that lies) · Type · Record
        (placeholder "(vault — no parent record)")
      - Folder input, placeholder "(target root — no folder)", with a Clear
      - a live line: "Files land at **pms.files** / 2026/orders/…"
      - confirm: "Upload N files to pms.files" + Cancel, progress while sending

5d. Folders keep their structure: each file's folder is
    `[typedPrefix, folderOf(file.webkitRelativePath)].filter(Boolean).join("/")`.
    Verify: `pleadings/2026/x.pdf` → `pleadings/2026`, and with prefix "archive" →
    `archive/pleadings/2026`.
    NOTE: Playwright's `setInputFiles` cannot set `webkitRelativePath`. To test
    this, build the File objects in the page with `Object.defineProperty` and
    assign them through a `DataTransfer`.

5e. Table columns to match SOAR: NAME | WHERE | TYPE | SIZE | MODIFIED | STATUS |
    actions. Type is the content type with `application/` and `image/` stripped;
    Size carries `· v2` on versioned files; Status shows `ready` or the processing
    state (`queued` / `processing…` / `failed` / `no text`) — an unindexed file is
    stored but not yet searchable, and its absence from a text search is the
    pipeline still working, not a miss.
    Row actions: Preview · Download · Delete (with a confirm).
    NOTE: cap the Type column width with the full value in `title`.
    `application/vnd.openxmlformats-…-spreadsheetml.sheet` is a real content type
    and it will push Delete off the right edge.
    NOTE: `e.stopPropagation()` on the actions cell — the row itself opens the file.

5f. A Search button next to the search box (typing filters what is on screen; the
    button is what asks the server — without it the distinction is invisible), a
    Clear, and a "⌁ how this works" disclosure at the foot naming the search
    endpoint and explaining the Where chip and `_vault`.

6. SIDEBAR — Tab and Shift+Tab open the type, not just focus it
================================================================================
Today Tab moves focus down the module rail but the content does not follow, so you
light up names without seeing any data. Make Tab / Shift+Tab inside the rail move
to the next/previous module AND navigate to it.

On the <nav> element, an onKeyDown that: ignores anything but Tab (and bails on
alt/ctrl/meta); finds `a.nav-item` links; locates `document.activeElement` among
them; bails if focus is not on one; computes next = index ± 1; **bails if that
falls off either end so Tab can leave the rail normally**; otherwise
preventDefault, focus the next link, and `navigate(href)`.

NOTE — scope this to the rail and nowhere else. Tab is also how you move between
form fields; hijacking it globally would throw you out of a half-filled New
<Record> form on every field. Write the guard-rail test for exactly that: open a
create dialog, press Tab three times, assert the URL is unchanged and the dialog
is still open. That test matters more than the feature.

Tests: frontend/e2e/nav-keyboard.spec.ts — Tab walks and opens each module, the
focused link and the open page agree, and the form case above.
